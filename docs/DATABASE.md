# Database

## Technology and migration

PostgreSQL 17 is the relational store. EF Core 10.0.12 with Npgsql 10.0.3 owns the schema. The current migration is `20260927153937_InitialFoundation` under `apps/api/src/Platform.Api/BuildingBlocks/Infrastructure/Migrations`.

Apply migrations explicitly with the command in the root README. The API does not migrate the database during startup.

## Current entities

Platform-level tables:

- `tenants`: tenant identity, slug, active flag, timestamps
- `asp_net_users` and supporting ASP.NET Core Identity tables: global user identity and secure password/token data
- `permissions`: globally defined permission codes grouped by module

Tenant-owned tables:

- `tenant_memberships`: active relationship between one platform user and one tenant
- `tenant_roles`: tenant-defined roles
- `role_permissions`: role-to-permission grants with repeated `tenant_id` for isolation/indexing
- `membership_roles`: membership-to-role grants with scope kind and optional scope ID

ASP.NET Identity's built-in global roles exist in the initial schema because the Identity store includes them, but product authorization uses `tenant_roles` and tenant membership grants. Application code must not use the built-in role tables for tenant authorization.

## Conventions

- Database identifiers use `snake_case`; index names use `ix_...`.
- Primary identifiers are UUID/`Guid`, generated by application code unless a future entity explicitly chooses a database default.
- Tenant-owned records implement `ITenantOwned` and have `tenant_id` in relevant indexes/constraints.
- Persisted technical timestamps are `DateTimeOffset` in UTC and end with `_at_utc`.
- Timestamp assignment uses `TimeProvider` in `PlatformDbContext`.
- Foreign keys use restrictive deletes where deleting a tenant/user could destroy owned history. Join rows may cascade from their aggregate owner as defined by the migration.
- Strings have explicit maximum lengths when the domain currently defines one.
- Unique constraints are tenant-aware where uniqueness is local to a tenant.

## Tenant enforcement

`PlatformDbContext` has explicit global query filters for every current tenant-owned entity. Its save convention requires an active `ICurrentTenant`, fills an empty tenant ID on new entities, and rejects an entity whose tenant differs from the request tenant. Raw SQL, `IgnoreQueryFilters`, bulk APIs, migrations, and background workers bypass or alter normal behavior and require explicit tenant constraints and tests.

## Lifecycle and concurrency

There is no universal soft-delete column. Domain aggregates should use archive/status fields where recovery/history is meaningful; immutable ledgers and audit records require different rules. Hard delete behavior must be decided per aggregate.

No general concurrency token is implemented yet because the current records are foundation configuration. Mutable operational aggregates should add PostgreSQL `xmin` or an explicit version token and expose conflict responses through the API.

## Time

Technical instants are stored in UTC. The server must not persist local machine time. Tenant/user timezone settings will affect display and future schedule interpretation; schedules should preserve the business timezone separately from generated UTC instants.

## Indexes and constraints

Important unique indexes include tenant slug, permission code, `(tenant_id, user_id)` membership, and `(tenant_id, name)` tenant role. Supporting indexes cover all foreign keys and tenant-first access paths used by membership/role grants.

## Future location data

Locations will start with `sites`, `location_types`, and a self-referencing `location_nodes` adjacency list. Every node will repeat tenant and site identity so constraints and queries can prevent cross-tenant or cross-site parents. The schema must not encode fixed Site/Building/Floor/Room columns.

## Migration history

| `20260927165712_TenantAdministrationAndLocations` | Platform-admin flag, tenant version, company profiles, sites, configurable location types, adjacency-list locations, audit events |

`user_sessions` stores user, optional tenant/membership context, authentication context, a SHA-256 refresh-secret hash, timestamps, revocation state, limited client metadata, and a concurrency version. Raw secrets and access tokens are never persisted. Existing users, memberships, and roles are backfilled active with non-empty versions. The migration registers Task #003 permissions and grants them to existing system Tenant Administrator roles.

## Task #002 schema and lifecycle

`company_profiles` is one-to-one with a tenant. `sites` and `location_types` use `(tenant_id, code)` uniqueness; `location_nodes` uses `(tenant_id, site_id, code)`. Composite foreign keys constrain every node to a site, tenant-owned type, and parent in the same tenant/site. Delete behavior is restrictive. Tenant, company, site, type, and location records use UUID optimistic-concurrency versions; stale writes return 409. No hard-delete API is exposed.

All three migrations were applied successfully to a healthy local PostgreSQL 17 Docker Compose instance and verified through EF Core's migration history on 2026-09-28. The Compose volume is persistent and local setup must not delete or recreate it.

## Task #006 schema

Migration `20260929191659_PreventiveMaintenance` adds `preventive_maintenance_plans`, `preventive_maintenance_checklist_items`, `preventive_maintenance_occurrences`, and `preventive_work_order_checklist_responses`. It extends `corrective_work_orders` with a type discriminator, nullable breakdown source, PM plan/occurrence links, and scheduled due time so existing CM rows and contracts remain valid.

## Service request schema

`service_request_categories` stores tenant-unique codes, English/Arabic names and descriptions, default priority, asset/location requirements, activation, ordering, and UUID concurrency. `service_requests` stores `SR-YYYY-NNNNNN`, site and optional facility location/asset links, requester, lifecycle timestamps, assignment, resolution, terminal reason, and a unique linked CM breakdown.

`service_request_assignments`, `service_request_notes`, and `service_request_activities` are append-only history. Composite tenant-aware foreign keys and restrictive deletes protect site, location, category, asset, breakdown, and request references. Lookup indexes cover tenant/number, site/status/priority, requester, assignee, asset, category, and linked breakdown.
